# §11 · "มันเพราะไหม" — วัดจริง แล้วแก้ให้เพราะขึ้น (2026-10-03)

> เจ้าของถามตรง ๆ ว่า backing track **เพราะหรือยัง** ถ้ายังไม่เพราะให้หาทางทำให้เพราะกว่านี้
> คำตอบรอบนี้ไม่ใช่ความรู้สึก — คอนเทนเนอร์นี้ไม่มีเสียง แต่มีตัวเลข
>
> งานรอบถัดไปที่ต่อจากตัวเลขในหัวข้อนี้: `24-plan-band-sound-next.md`

## 11.1 วิธีวัด (ไม่ใช่การเดา)

`play-along-band.ts` เป็น Web Audio ล้วน ๆ (ออสซิเลเตอร์ ฟิลเตอร์ คอมเพรสเซอร์ ดีเลย์)
คอนเทนเนอร์นี้ไม่มีเบราว์เซอร์และไม่มีลำโพง แต่เราเขียน **Web Audio ชิ้นเล็กที่ตรงพอ**
แล้วขับ **`play-along-band.ts` ตัวจริง** ผ่านมัน → ได้เสียงจริงเป็นตัวเลข

| ไฟล์ | ทำอะไร |
|---|---|
| `scripts/band-audio-lab.mjs` | Web Audio นอกไลน์: AudioParam (ramp/เป้าหมาย) · ออสซิเลเตอร์ 4 ชนิด **ผ่าน PolyBLEP** · ฟิลเตอร์ RBJ · คอมเพรสเซอร์ · ดีเลย์ไลน์จริง · **บัสของแอปเอง** (gain 0.9 + reverb 1.5 วิ) · convolver แบบ overlap-save · FFT/Welch |
| `scripts/analyze-band-sound.mjs` | เรนเดอร์เพลงจริงจาก `songs-data.ts` ผ่าน `songChordBars()` ตัวเดียวกับเกม แล้ววัด |

สิ่งที่โมเดลไว้ตรงตามสเปก: ramp ของ AudioParam จบที่เวลาที่ระบุ (ตัวโค้ดเขียน
`exponentialRampToValueAtTime(0.0001, when + 0.22)` หมายถึง **จบ** ที่ 0.22 วิ)
· ฟิลเตอร์คำนวณใหม่ทุก 64 ตัวอย่าง · เสียง saw/square ผ่าน PolyBLEP
**ถ้าไม่ใช้ PolyBLEP คลื่นจะแอลิแอสแล้วตัวเลข "ความสว่าง" ทุกตัวเป็นเท็จ**

ที่ **โดยประมาณ** (บอกตรง ๆ): คอมเพรสเซอร์ (ผมใช้กฎสถิตตามสเปก ไม่ใช่ WebKit ตัวจริง)
· ระหว่างปิดลูปของดีเลย์ 1 บล็อก (5.8 มิลลิวินาที) · ตารางเสียงของ noise ใช้ seed คงที่
(ของจริงใช้ `Math.random()` ถ้าไม่งั้นตัวเลขขยับทุกครั้งที่รัน)

> **คำเตือนที่ต้องรู้ก่อนอ่านตัวเลข:** ตัวเลขรอบแรกในหัวข้อนี้ถูก **ถอนบางส่วน** เพราะแล็บเคย
> ไม่ทำตามที่เบราว์เซอร์ทำกับ reverb (`ConvolverNode.normalize` default `true`) — อ่าน **§11.7**
> ก่อนอ้างเลขอะไรจากที่นี่ โดยเฉพาะบรรทัดที่ขึ้นว่า "หลังบัส"

## 11.2 ตัวเลขก่อนแก้ (ระดับ "ปกติ", 8 ห้อง, combo 12) — เพราะไหม

> ⚠️ **ตารางนี้ถูกถอนบางส่วนเมื่อ 2026-10-03** — บรรทัดที่วัด "ผ่านบัส" ยกเลิก เพราะตัวเลข
> เหล่านั้นมาจากแล็บที่ไม่ได้ทำตามที่เบราว์เซอร์ทำ อ่าน **§11.7** ก่อน
> ที่ยังใช้ได้: สัดส่วนเสียงตามย่านความถี่ · ศูนย์ถ่วงสเปกตรัม · ช่วงดัง (arc) ·
> การเดินที่นำของเบส · การเทียบกับโน้ตผู้เล่น

| วัด | ผล | อ่านว่า |
|---|---|---|
| ยอดสูงสุดหลังบัส | **+5.9 … +7.0 dBFS** | เกิน 0 dBFS 7 dB — **แตก** ทุกจังหวะหนัก |
| ตัวอย่างที่ clip (จาก ~950,000) | **26,000 – 58,000** (3–6 %) | เสียงแตกคือเสียงที่ฟังแล้ว "ถูก" |
| พลังงานต่ำกว่า 250 Hz | **90–97 %** | มีแต่เบสกับกลอง กลาง/บนแทบไม่มี → ทึบ |
| ศูนย์ถ่วงสเปกตรัม | **110–210 Hz** | เทียบเพลงที่มีคนเล่นจริง ≈ 1–3 kHz |
| พลังงาน C4–C6 (ที่เมโลดี้อยู่) | 8–26 % | วงกินอยู่ในที่ของผู้เล่น |
| ช่วงดังระหว่างเพลง (ท่อนละ 4 ห้อง) | **1–2 dB** | เล่นเท่ากันทุกห้อง = **นาฬิกาที่มีโน้ต** |
| ห้องใน C4–C6 เทียบกับโน้ตของผู้เล่น | median **−11 dB**, p90 **+1 dB** | ที่ 90% ของโน้ต วงเท่ากับโน้ตผู้เล่น → ผู้เล่นจม |
| เบสในหนึ่งห้อง | root–fifth ซ้ำ ๆ | ไม่มีการเดินที่นำ |

**คำตอบ: ยังไม่เพราะ** และไม่ใช่เพราะขาดเสียง — เพราะ **มี 3 อย่างผิดที่ฟังออก**
(เกิน full scale · ทึบจนไม่มีชั้น · แบนจนไม่มีเป็นวรรค)

## 11.3 ที่แก้ (M7) และตัวเลองหลังแก้

| งาน | ทำอะไร |
|---|---|
| **M7.1 เหลือ headroom** | ต่อ `air` (high-shelf +4.5 dB @ 4.2 kHz) → **soft saturator** `y = x/(1+\|x\|³)^⅓` (ใสได้ 1 เป๊ะ จึงไม่เพิ่มความดัง) → คอมเพรสเซอร์แรงขึ้น · master ลดเหลือ `BAND_LEVELS × 0.21` |
| **M7.2 สมดุลเสียง** | เบส/กลองลดลง แผ่นเสียงและเสียงนำขึ้น (0.026 → 0.04, cutoff 1350 → 1900) ซีลสตา/ฮาร์ปซิคอร์ด/ออร์แกนส่งเข้าเอโค้มากขึ้น |
| **M7.3 รูปร่างของเพลง (dynamics)** | เส้นโค้ง 4 ห้อง: ถอย → ขึ้น → ยกตอนห้องที่ 4 → หายใจ บีต 1 หนักกว่า ห้องแรก 2 อยู่ข้างหลัง ห้องสุดท้ายเอ่งเข้า + แตรลูยเข้าห้องก่อนปิด |
| **M7.4 เว้นที่ให้เมโลดี้** | ผู้เรียกส่ง `mel` (โน้ตของผู้เล่น) เข้าไป · ที่ที่เมโลดี้กำลังดัง **แผ่นเสียง/เบรส/สาย/อาร์ปีโจลงหนึ่งอ็อกเตฟ** และเส้นสตริงเล่นเฉพาะช่องว่าง |
| **M7.5 เบสเดินที่นำ** | ครึ่งห้องสุดท้ายก่อนคอร์ดเปลี่ยน เดินขั้นเข้าหาเลขฐานคอร์ดใหม่ แทนการซ้ำรูต |

## 11.4 ⚠️ ข้อความเดิมถูกถอน — บัสไม่ได้บูมอย่างที่เคยเขียนไว้

> **หัวข้อนี้เขียนใหม่ทั้งหมดเมื่อ 2026-10-03** ฉบับก่อนบอกว่าบัสของแอป
> "+17 ถึง +18 dB" และนั่น **ไม่จริง** ดู §11.7

`audioBus()` ใน `music-engine.tsx` สร้าง reverb impulse response แบบนี้

```js
d[i] = (Math.random() * 2 - 1) * Math.pow(1 - i / len, 2.6);   // len = 1.5 s
...
wet.gain.value = 0.13;
```

**แต่ ConvolverNode มี `normalize` ซึ่ง default เป็น `true`** (MDN: "its default value
is true in order to achieve a more uniform output level from the convolver, when
loaded with diverse impulse responses"; สเปก Web Audio 1.1: เมื่อเป็นจริง node จะ
"perform a scaled RMS-power analysis of the buffer" ก่อน convolve) และโค้ดนี้ไม่เคย
แตะ `normalize` → **เบราว์เซอร์ normalize ให้เรียบร้อยแล้ว**

วัดจริงด้วย `scripts/verify-audio-bus-ir.mjs` (โน้ตเดียวจาก `playPianoNote` ผ่านบัสตัวจริง):

| วัด | ผล |
|---|---|
| wet/dry | **−14.8 dB** (คาดจาก wet gain 0.13 = −17.7 dB ใกล้เคียง เพราะหางซี้เติมพลังงาน) |
| ยอดสูงสุดหลังบัส | **−7.9 dBFS** |
| ตัวอย่างที่ clip | **0** |
| เสียงห้องค้างหลังโน้ตดังแล้ว 1 วิ | −49.9 dB จากยอด |

แปลว่า **ห้องนี้เบากว่าตัวโน้ตถูกต้องและไม่แตะ** ไม่ใช่เหตุผลที่เพลงราบหรือแตก
"เพราะ" จริง ๆ อยู่ที่อื่น — ที่สัดส่วนเสียงเอง (§11.2/11.3)

### สิ่งที่แก้จริง (เล็ก แต่วัดได้ว่ามีผล)

เพิ่ม **pre-delay 18 ms** หน้าหาง เพราะห้องจริงมีระยะ — เสียงมาถึงก่อนเสียงสะท้อน
วัดผลของมัน (สัดส่วนเสียงห้องที่มาถึงใน 40 ms แรก เทียบกับ 200 ms ถัดไป):

| ตอบสนอง | เสียงห้องบนช่วง attack |
|---|---|
| เดิม (หางเริ่มทันที) | −12.6 dB |
| **มี pre-delay 18 ms** | **−16.9 dB** |

คือ reverb ที่ทับลงไปบนช่วง attack ของเปียโนลดลง 3.7 dB → โน้ตเปิดตัวชัดขึ้น
(ค่าตัวเลขเดิมที่ตั้งไว้คือ 0.13 dB ที่คาดจาก wet gain และพิสูจน์ได้ว่าเป็นห้อง ไม่ใช่น้ำท่วม
การขึ้นเป็น 0.20 วัดได้ wet/dry = −11.0 dB ซึ่งชิดขอบเกินไป → **คง 0.13 ไว้**)

## 11.7 บันทึกการถอนตัวเลข (2026-10-03) — อ่านก่อนใช้ตัวเลขจาก §11.2/11.3

ตัวเลขรอบแรกวัดผ่าน `appBus()` ใน `scripts/band-audio-lab.mjs` ซึ่งเรียก `convolve()` ดิบ
ไม่ normalize แต่ **เบราว์เซอร์ normalize เสมอ** เพราะ `ConvolverNode.normalize`
default `true`

ผลคือแล็บนั้นบูมกว่าแอปจริงราว **+17…+18 dB** ทั้งชุด และยืนยันได้ตรง ๆ ว่า

1. บัสของแอป **ไม่เคย** บูม เสียงทุกอย่างในแอปไม่เคยถูกกลั่นในห้องที่บูมกว่าตัวเอง
2. คำอธิบายที่เคยให้ว่า "ช่วงดังของเพลงถูกราบลงเพราะห้องที่บูม" **ไม่จริง** เหตุผลที่วัดได้จริง
   คือ `arcAt()` ที่เพิ่มเข้าไปเอง (วัดบนสัญญาณดิด: 1.5–6.9 dB)
3. ตัวเลข "ก่อน/หลัง" ที่วัด **ผ่านบัส** ทั้งหมดยกเลิก ได้แก่ ยอดสูงสุด · RMS · clip ·
   สัดส่วนพลังงานตามย่าน · ศูนย์ถ่วงสเปกตรัม · arc หลังบัส · การกลบเมโลดี้ · เหลือห้อง
4. ตัวเลขที่ **ไม่** ผ่านบัสจึงยังใช้ได้: `melBusy()` · เบสเดินที่นำ · master gain ×0.21 ·
