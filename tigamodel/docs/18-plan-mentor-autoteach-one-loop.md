## 0. คำตอบสั้น

สองฟีเจอร์นี้ไม่ได้ "ต่อกันไม่ครบ" แค่หน้าตาต่างกัน — **มันอ่านคนละแหล่งข้อมูลกันอยู่**
วันนี้ "ครูในป๊อปอัป" กับ "หน้า Daily Mentor" ตอบคำถามเดียวกัน ("ตอนนี้ควรให้เขาฝึกอะไร")
ออกมาคนละชิด เพราะอ่านคนละ localStorage key และไม่มีใครเขียนลงชั้นข้อมูลกลาง (`learning_*`) เลย

แผนนี้คือ **สร้างวงจรเดียว แล้วให้สองฟีเจอร์เป็นสองหน้าต่างของวงจรเดียวกัน**
- **Daily Mentor = ที่ที่ครูวางแผน** (เห็นว่าครูคิดอะไร จากหลักฐานอะไร ได้ผลไหม)
- **Auto Teaching = ที่ครูไปหาผู้เรียน** (ยิงป๊อปอัปตามจังหวะ แต่ยิง "คำสั่งเดียวกัน" เป๊ะ)
- UX: หน้า Mentor **สั้นลง** (การ์ดเดียวบนสุด = ทำอะไรต่อ) ไม่ใช่เพิ่มกล่องใหม่ 3 กล่อง

## 3. หลักการ: "วงจรเดียว" (One loop) — ไม่ใช่สองฟีเจอร์ที่พยายามคุยกัน

```
  [ซ้อมจริง]  ──►  Trace (หลักฐาน)  ──►  Diagnosis (สมมติฐาน+ความมั่นใจ)
                                        │
                                        ▼
                       ONE DECISION  (การ์ดเดียว: ทำอะไร · ทำกี่นาที · ทำไม)
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
     Auto-Teach popup   Mentor card   Lesson/drill เปิดตรง
     (ส่งตามจังหวะ)      (เช็กว่าทำไม)  (ไม่ต้องหาเอง)
              └─────────────┼─────────────┘
                            ▼
                    Outcome (วัดได้จริง: ก่อน/หลัง)
                            │
                            ▼
              กลับเข้า Trace → weights ของกลยุทธ์ → ครูดีขึ้นเอง
```

**กฎเหล็ก 4 ข้อของวงจร (ตรวจได้อัตโนมัติ)**
1. **Decision เดียวต่อหนึ่งช่วงเวลา** — ป๊อปอัปกับการ์ดใน Mentor ต้องมาจาก decision object เดียวกัน (เอา id เดียวกัน) ถ้าไม่ใช่ = บั๊ก มี smoke กัน
2. **No data → ไม่มีคำแนะนำ** — ไม่เดา ไม่เติมค่า 0 แสดง "ยังไม่มีข้อมูล" (หลักเดียวกับ `SKILL_MIN_N = 8` ที่มีอยู่วันนี้)
3. **confidence < 0.5 ห้ามขยับระดับ** — เหมือน `skill-state-plans.js` ที่เขียนไว้แล้ว: สังเกตต่อ ไม่สรุป
4. **ปิดสวิตช์ = พฤติกรมเดิม 100%** — ทุกขั้นใหม่ต้องมี kill switch ผ่าน `admin_set_app_setting` ค่าเริ่มต้น OFF

## 4. แผน 6 ระลอก (เรียงตามลำดับที่ต้องทำจริง ไม่ใช่ตามความสวยงามของฟีเจอร์)

### P0 — ปลดล็อกประตูที่กลืนทุก trace ✅ (เสร็จ 2026-10-02)
- **ทำ:** แทน `sb.auth._sessionReady()` (ไม่มีอยู่จริงใน supabase-js 2.x) ด้วย `learning-session-gate.ts` — 3 กฎ pure: "ยังไม่รู้ → ลองเขียน (ให้ RLS เป็นผู้ตัดสิน)", "รู้ว่าไม่ได้ล็อกอิน → ไม่เขียน + ทิ้งคิว", "มี user → เขียน" พร้อม `refreshSessionUser()` อ่าน `getSession()` จริงตอนบูตและตาม `onAuthStateChange` · flush คิวหลังรู้สถานะแล้ว (เดิม flush ก่อนรู้)
- **พิสูจน์แล้วว่าไม่ใช่ปัญหา DB:** `scripts/check-learning-wire.mjs` (read-only, live) → 8/8 RPC มีจริง + ชื่อ argument ตรงกับ client ทุกตัว → ต่อเข้า plan-check เป็น `m05-learning-wire-live` เพื่อกันไม่ให้เงียบอีก
- **กันไม่ให้กลับมาอีก:** `tigamodel/scripts/smoke-learning-wire.mjs` 13/13 (มี regression case ยืนยันว่าโค้ดเก่าตอบว่า "ไม่ได้ล็อกอิน" ทั้งที่ผู้เรียนล็อกอินแล้ว) ต่อเข้า `npm run verify:tiga`
- **ยังต้องทำ (รอข้อมูลจริง):** กดซ้อมจริง 1 รอบ แล้วรัน `node scripts/check-learning-wire.mjs` อีกครั้ง — `learning_practice_events` / `learning_observations` ต้องเริ่มขยับจาก 0
- **สิ่งที่ P0 นี้ไม่ได้ทำ (อย่าคิดว่าทำแล้ว):** ยังไม่ได้เพิ่มการเขียนที่ `logActivity` สำหรับโหมดที่ไม่ใช่ practice-mode (ear/read/drill) — ต้องมีเกณฑ์กันปริมาณเขียนก่อน จึงจะทำต่อในระลอบถัดไป

### P1 — `learnerSignal()`: หน่วยตัดสินใจเดียว ที่ทั้งสองหน้าใช้ร่วมกัน ✅
- **ทำ:** โมดูล pure หนึ่งตัว (`learner-signal.ts`) รับ trace ที่มี → คืน `{ weakest, skillScores, drillPlan, minutes, confidence, evidence[] , nextAction }` — เลียบ `weightedStruggles` + `computeSkillScores` + `pickDrillPlan` เข้าด้วยกัน โดย **คงกติกาความซื่อสัตย์ของเดิมทุกข้อ** (half-life, ขั้นต่ำ 8 ครั้ง, confidence ≥ 0.5, ไม่มีข้อมูล = null)
- **กติกา:** ไม่มี `localStorage` ในตัวโมดูล — รับข้อมูลเข้ามา คืนค่ากลับ ทดสอบได้ด้วย fixture (ตามแนว `smoke-*.mjs` ที่มีอยู่)
- **เกณฑ์วัด:** smoke ใหม่ ≥ 15 เคส: ไม่มีข้อมูล→null · 6 จุดอ่อน→ยังอันดับถูก · ability ต่ำ+มั่นใจ→ผ่อนระดับ · ability ต่ำ+มั่นใจต่ำ→**ไม่ขยับ** · เรียงซ้ำได้เหมือนเดิม (deterministic)
- **UX ที่ได้:** ทั้งสองหน้าตอบเหมือนกันเป๊ะ เพราะอ่าน object เดียวกัน

### P2 — Mentor: หน้าจอเดียว "วันนี้ทำอะไร" + เหตุผลที่มีหลักฐาน ✅
- **ทำ:** การ์ดเดียวบนสุดของ `CoachPage` = `nextAction` จาก P1: ชื่อแบบฝึก · นาที · **เหตุผล 1 บรรทัดที่มีตัวเลขจริง** (`จาก 42 ครั้ง · พลาด 18%`) · ปุ่มเดียว "ฝึกเลย" → เปิด drill/เพลงที่เลือกไว้จริง (`resolveCoachStep` / `goToCoachStep` ที่มีอยู่แล้ว)
- **ทำไมง่ายขึ้น:** สิ่งที่มีอยู่ (7-day chart, คะแนนทักษะ 7 ด้าน, จุดที่พลาด, แนวโน้มรายเดือน, การ์ดรายงาน, แผน 7 วัน) ย้ายไปอยู่ใต้หัวข้อ **"ดูเพิ่มเติม"** แบบพับได้ — ไม่ลบอะไรทิ้ง แต่หน้าแรกเหลือ "ทำอะไรต่อ"
- **เกณฑ์วัด:** browser pass: เปิดหน้า Mentor แล้วเห็นการ์ด action เดียวใน 3 วินาที (ไม่ต้องเลื่อน) · กดปุ่มแล้วลงจบใน drill จริง 1 ท่าที่บอกไว้
- **กติกาคุณภาพ:** ถ้าไม่มีข้อมูลพอ → การ์ดเป็น "ยังซ้อมไม่พอให้บอก — ลองเล่น 2 รอบ" พร้อมปุ่มไปเล่น ไม่ใช่การ์ดว่าง

### P3 — Auto-Teach ยิง "คำสั่งเดียวกัน" (delivery ของ decision เดียว) ✅
- **ทำ:** `fetchAutoTeachTip` ไม่ตัดสินใจเองอีกต่อไป — ขอ `nextAction` เดียวกับ P1 แล้วเอาไปแสดง (ข้อความยังผ่าน teaching loop + `validateTip` + fallback เดิม) ถ้า Mentor เพิ่งบอกเรื่องเดียวกันภายใน 24 ชม. → ป๊อปอัปนั้นถือว่า "ส่งแล้ว" ไม่ยิงซ้ำ (กันผู้เรียนเจอคำเดียวกันสองที่)
- **คงของเดิม:** priority guard, cap ไม่เกิน 2 การ์ด/วัน, ไม่ยิงกลางเพลง, premium gating (รอเจ้าของตัดสินเรื่อง gate ตามข้อ 8)
- **เกณฑ์วัด:** smoke ยืนยันว่า decision id ที่ป๊อปอัปใช้ = decision id ที่ Mentor แสดง · ไม่มีการยิงซ้ำใน 24 ชม. · ปิดสวิตช์แล้ว path เดิม 100%

### P4 — หลักฐานผล: ทุกคำแนะนำมี "ก่อน/หลัง" ที่วัดได้ ✅
- **ทำ:** ย้ายวงจรปิดจาก localStorage (`tg_atip_outcomes`, 40 ราย) ไปเป็น trace จริง: เปิด advice → `learningIntervene` + snapshot; จบ session ถัดไป → `recordFollowUpPractice(feature, ok, accAfter)` ผูกด้วย intervention id
- **ที่แสดง:** ในการ์ด Mentor บรรทัดเดียว — "เมื่อวานนี้ครูแนะนำ X → วันนี้แม่นขึ้น 8% (จาก 62→70)" · **ไม่มีข้อมูลพอ = ไม่ขึ้นบรรทัดนี้** (ห้ามเขียน "กำลังดีขึ้น!" ลอย ๆ ตามกติกา philosophy เดิม)
- **ผลข้างเคียงที่ต้องการ:** `outcomes` ใน DB เริ่มมีของจริง → ปลดล็อก m17 (analyzer) / m18 (skill state จริง) ที่ค้างอยู่

### P5 — ครูที่ปรับตัวเอง + ปุ่มหลังบ้าน ✅ (โค้ด + ปุ่มใน Model Lab แล้ว · ผลจริงยังรอ outcomes)
- **ทำ:** เมื่อ P4 มีข้อมูลพอ → ต่อ `strategy-analyzer` เข้ากับ `tiga_policy_weights` (มีโค้ดและ kill switch พร้อมแล้ว) และแสดงผลใน Model Lab ว่า "กลยุทธ์ไหนได้ผลกับใคร" — **ยังไม่เปิดใช้เอง** ปุ่มสวิตช์เหมือนเดิม (เจ้าของกดเอง)
- **เกณฑ์วัด:** เมื่อสวิตช์เปิด → outcomes ≥ 50 แล้ว weight ที่ได้ต่างจาก baseline ตามเกณฑ์ใน m17 · ปิด = เดิมเป๊ะ (byte-identical)

## 5. UX/UI — กฎที่ห้ามละเมิด (เจ้าของ: "ยังต้องใช้งานง่าย")

1. **หน้าแรก = 1 คำตอบ** หน้าไหนก็ตาม ผู้เรียนต้องเห็นคำตอบว่า "ตอนนี้ทำอะไร" โดยไม่ต้องเลื่อน/เปิดเมนู
2. **ไม่เพิ่มกล่องใหม่นอกการ์ด action** ทุกอย่างใหม่ที่ต้องอธิบาย ย้ายไปใต้ "ดูเพิ่มเติม"
3. **ปุ่มหลัก 1 ปุ่ม** ปุ่มรอง ≤ 2 (เช่น "ดูรายละเอียด", "ข้ามวันนี้") — ปุ่มที่ต้องอธิบายก่อนกดคือปุ่มที่ออกแบบมาไม่ดี
4. **เหตุผลต้องมีตัวเลขจริงเสมอ** (หรือเขียนว่า "ยังไม่มีข้อมูลพอ") — ห้ามคำโปรยที่ไม่มีหลักฐาน
5. **ไม่มีตัวเลขปลอม** ช่องว่าง = "ยังไม่มีข้อมูล" ไม่ใช่ 0% (กติกาเดียวกับ scorecard ด่าน 12)
6. **คำเดียวในหนึ่งครั้ง** ถ้าป๊อปอัปบอกอะไร ให้หน้า Mentor เป็นแหล่งเดียวที่เจาะลึก ไม่ใช่สองบทสนทนาที่ไม่รู้จักกัน
7. **3 ภาษาตั้งแต่ต้น** ทุกสตริงใหม่ครบ th/en/zh ผ่าน `tr()` (กันบั๊ก React #31 ตามที่เพิ่งแก้)
8. **ไม่มีคำศัพท์วิชาการเกินระดับผู้เรียน** — โทนตาม `learnerTone()` ที่มีอยู่แล้ว (ชั้นต้น/กลาง/สูง)

### 11.2 สิ่งที่แก้ (โค้ดเสร็จ)

**รอบแรก (โหลดช้า · อ่านไม่ครบ):**
- **`speech.ts`** — `ttsChunks(text, max, firstMax)` ตัดข้อความเป็นก้อน: ก้อนแรกสั้น (`TTS_FIRST_CHUNK_CHARS` = 380) เพื่อเริ่มได้เร็ว ก้อนถัดไปใหญ่ขึ้น (`TTS_CHUNK_CHARS` = 700) และก้อนถัดไปถูกโหลดไว้ล่วงหน้าขณะก้อนก่อนหน้ายังเล่น
- **`speech.ts`** — `CHAT_TTS_RATE` = **1.15** (Voice Tutor ยังใช้ `TTS_RATE` เท่าเดิม) และ `chat-ui.tsx` ใช้ค่านี้แทน `1`
- **`speech.ts`** — **คิดโควตาครั้งเดียวทั้งข้อความ** (ธง `msgOpts.charged`): ถ้าโควตาวันนี้ไม่พอข้อความนี้เลย → ไม่เริ่มเลย → ส่งให้เสียงเครื่องอ่าน**ครบทั้งข้อความ** (เดิมหยุดกลางข้อความ)
- **`supabase/functions/piano-tts/index.ts`** — `Promise.all([chatVoiceAllowed, resolveTtsConfig])` ตัดหนึ่ง round trip (~100–300 มิลลิวินาที) ⚠️ **ยังไม่ได้ deploy**
