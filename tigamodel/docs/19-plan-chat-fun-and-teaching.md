# 19 — แผนทำให้ TIGA CHAT เร็วขึ้น · ถูกลง · สนุกขึ้น · สอนรู้เรื่องขึ้น (เจ้าของสั่ง 2026-10-02)

คำสั่งเดิม: *“เขียนแผนพัฒนาฟีเจอร์ tiga chat ให้ใช้แล้วสนุกกว่านี้… ให้รู้สึกสนุกกว่านี้ มีความรู้สึกของเกมมากขึ้น”* → รอบสอง: *“ปรับปรุงแผนให้ดีขึ้นอีก เน้นประสิทธิภาพ ความเร็ว ต้นทุนที่ถูกลง และสนุกขึ้น ดีขึ้นอีกล้านเท่า”*

**เอกสารนี้เป็นแผน ยังไม่ได้แก้โค้ดผลิตภัณฑ์** มีไฟล์เดียวที่เพิ่ม: `scripts/measure-chat-cost.mjs` (สคริปต์วัด ไม่กระทบแอป) เพราะตัวเลขในเอกสารนี้ต้อง**รันซ้ำได้** ไม่ใช่ตัวเลขที่ผมพิมพ์มาเอง

## 0. บทสรุปสำหรับเจ้าของ

**ข้อค้นพบใหญ่ที่สุดรอบนี้: แชทแพงและช้าเพราะส่งคำถาม “minor chord ต่างจาก major ยังไง” ไปพร้อมกับข้อความ 1.39 ล้านตัวอักษร** — คือทั้งฐานความรู้ 17,246 รายการ (1.96 ล้านตัวอักษร) ถูกยัดเข้าไปทั้งก้อน เพราะคำว่า “ต่างจาก/chord/major” ไปโดนหลายหมวดพร้อมกัน

| ตัวเลข (วัดจากโมดูลจริง) | ค่า |
|---|---|
| ฐานความรู้ทั้งหมด | **17,246 รายการ · 1,960,702 ตัวอักษร** |
| ข้อความ prompt ส่วนที่คงที่ (persona + FINGERING + THEORY + student + coach) | **8,121 ตัวอักษร** |
| **คำถามทั่วไป (median จาก 20 คำถามจริง)** | **48,889 ตัวอักษร** |
| คำถามที่แย่ที่สุด (“minor chord ต่างจาก major”, “อะไรคือ inversion”, “ต่าง chord กับ triad”) | **1,392,012 ตัวอักษร = 28.5 เท่าของ median** |
| ประหยัดถ้าเปิดสวิตช์ hot path (เพดาน 8,000 ตัวอักษร) | **median −67% · แย่ที่สุด −99%** |

**แปลว่า:** คำถามทฤษฎีพื้นฐาน (คือคำถามที่ครูต้องตอบเก่งที่สุด) แพงที่สุดในระบบ และแพงเพราะส่งข้อมูลที่ครูไม่ได้ใช้ — ไม่ใช่เพราะโมเดลไม่เก่ง

รันซ้ำได้: `node scripts/measure-chat-cost.mjs`

## 1. ต้นทุนและความเร็ว — วิเคราะห์จากโค้ดจริง

### 1.1 หน้าตาแชททำอะไรต่อคำถามหนึ่งข้อ

```
พิมพ์ → เสียง C5 → FAQ match? → (ใช่: ตอบในแอป + payForAsk)
                          → (ไม่) → requireLogin → free quota → Jev pre-check → callClaude()
callClaude: cost governor (รอ) → system prompt (สร้าง 1 ครั้ง) → streaming
            → ถ้าค้าง: silent retry → JSON → ถ้ายังล้ม: รอ 4 วิ → รอบ 2 → KB fallback
flush() เขียนหน้าจอทีละ ~16fps
```

**จุดที่กินเวลา/เงิน เรียงตามขนาด**

| # | อะไร | ขนาดจริง | หลักฐาน |
|---|---|---|---|
| 1 | **KB slice ต่อคำถาม** | median 40,768 / max **1,383,891** ตัวอักษร | `getKBContext()` — วัดจากโมดูลจริง |
| 2 | **THEORY_REF ทุกคำถาม** | 4,070 ตัวอักษร | `music-engine.tsx:329` — ต้องใช้จริงทุกคำถามไหม |
| 3 | **FINGERING_REF ทุกคำถาม** | 1,142 ตัวอักษร | `music-engine.tsx:300` — เกือบทั้งหมดเป็นตารางนิ้ว 12 คีย์ |
| 4 | **Jev pre-check** | รอได้ถึง `PRECHECK_BUDGET_MS` | เป็นการเรียกโมเดล **1 รอบเพิ่ม** ต่อคำถาม |
| 5 | **ประวัติสนทนา** | 6 turn ล่าสุด | `buildAlternatingHistory(msgs, 6)` — บันทึกไว้ 24 ข้อ แต่ส่งไปแค่ 6 |
| 6 | **KB fallback** | — | สวิตช์ปิดอยู่ → error bubble (ตาม `AGENTS.md` ให้เจ้าของเปิด) |
| 7 | **withAiCache** | **ไม่ได้ใช้กับแชทเลย** | มีแต่ใช้กับ `coachTip`, `aiReport`, `songAnalysis` |

### 1.2 ช่องรั่วที่วัดได้ 4 อัน เรียงตามผลกระทบ

#### รั่ว #1 (ใหญ่ที่สุด) · คำขอที่ตรงกับหลายหมวด = ได้ KB ทั้งก้อน

```js
// tigamodel/web.js:1314 getKBContext(matchText) — เลือกบล็อกด้วยการจับคำเข้า
```

คำว่า “minor chord ต่างจาก major” โดน **minor** + **chord** + **major** → หลายหมวดพร้อมกัน → รวมกันเป็น 1.38 ล้านตัวอักษร

**แก้ได้ 3 ทาง (เรียงตามความเสี่ยง):**

| ทาง | ทำอะไร | ผล | ความเสี่ยง |
|---|---|---|---|
| **ก · เปิดสวิตช์ที่มีอยู่แล้ว** | `app_settings.tiga_kb_hot_path = {enabled:true}` | median −67% · แย่ที่สุด −99% · คำตอบยังครบเพราะเพดาน 8,000 ตัวอักษรถูกเลือกมาแล้ว | **สิทธิ์เจ้าของเท่านั้น** (`AGENTS.md`: ห้ามเปิดจากโค้ด) |
| **ข · เพดานชั่น client** | เพิ่มเพดานกันบางใน `use-chat.ts` (เช่น 40,000) ไม่แตะสวิตช์ | ตัดหาง 99% ทิ้งทันที | **ต้องระวัง — ทำให้สวิตช์เป็นตาขาว** ควรมีแผนแก้ KB ควบคู่ |
| **ค · ซ่อมตัวเลือกเอง** | จำกัดการจับคำให้ตรงหมวดกว่านี้ | แก้ที่ต้นเหตุ | กระทบคุณภาพคำตอบ → ต้องวัด |

**ผมแนะนำ: ทาง ก (เปิดสวิตช์) แล้วค่อย ค** — แต่ต้องพิสูจน์คุณภาพคำตอบก่อน ดู §1.4

#### รั่ว #2 · บล็อกคงที่ส่งทุกคำถาม แม้ไม่เกี่ยว

`THEORY_REF` 4,070 + `FINGERING_REF` 1,142 = **5,212 ตัวอักษรทุกคำถาม** ทั้งที่ครูหลายคำถามไม่ต้องการ (เช่น “แนะนำเพลงยุคบาโรก” ไม่ต้องมีตารางนิ้ว)

**แก้:** ส่งเฉพาะที่เกี่ยว — regex เดียวกับ `songTalk` ที่มีอยู่แล้ว (`use-chat.ts:352`) ขยายเป็น: ถามเรื่องทฤษฎี/นิ้ว/บทเพลง → ส่ง · ถามเรื่องประวัติ/การตลาด → ไม่ต้องส่ง

> **ข้อควรระวังสำคัญ:** บล็อกสองนี้คือแหล่งที่ทำให้ครู **ไม่กลับคำสะกดผิด** (ตาม comment ใน `music-engine.tsx`) — ตัดแล้วคุณภาพอาจตก ต้องวัดคำตอบหลังตัดเทียบกับก่อน ไม่ใช่ตัดเพราะเบา

#### รั่ว #3 · แชทไม่มี cache เลย

```ts
// ai-cache.ts:44 withAiCache(namespace, keyBody, ttlMs, fetcher) — มีของแล้ว ใช้กับ 3 ที่
// chat ไม่เรียกเลยแม้แต่ครั้งเดียว
```

`coachTip` (1 ชม.), `aiReport` (24 ชม.), `songAnalysis` (24 ชม.) มี cache · **แชทไม่มี** — ถามคำถามเดิมซ้ำ = จ่ายเต็มทุกครั้ง

**แก้:** ครอบคำถามที่ตรงกับ FAQ ไม่แล้วด้วย cache ชั้นกลาง (namespace `chat`, TTL สั้น ~1 ชม., กุญแจรวม `lang` + ข้อความ + บริบทที่มีผล) — คำถามซ้ำในวันเดียวกัน (ซึ่งเกิดจริง: ผู้เรียนล้มที่เรื่องเดิมแล้วถามซ้ำ) จะไม่เข้าโมเดล

> **ต้องระวังเรื่องความเป็นส่วนตัว:** คำตอบที่แคชไว้คือคำตอบที่ผูกกับข้อมูลผู้เรียนคนนั้น — กุญแจจึงต้องรวม `studentBlock`/`coachBlock`/memory ด้วย ไม่ใช่แค่ข้อความ ไม่งั้นคนหนึ่งจะได้คำตอบที่อ้างตัวเลขของอีกคน

#### รั่ว #4 · Jev pre-check คือการเรียกโมเดลเพิ่ม 1 รอบ ทุกคำถาม

`jevPrecheckBounded()` ถูกจำกัดเวลาไว้แล้ว (`PRECHECK_BUDGET_MS`) ซึ่งดี — แต่ถ้ามันไม่ทัน คำถามนั้น **เสียเงินค่า pre-check เปล่า ๆ**

**แก้:** เก็บผล pre-check ลง cache สั้น (เช่น 10 นาที) ตาม hash ของข้อความ — ถามซ้ำ/ถามต่อ → ไม่ต้องจ่ายซ้ำ

### 1.3 ความเร็ว: ตอนนี้ช้าตรงไหน (แยกความเร็วออกจากต้นทุน)

ความเร็วของคำตอบครูขึ้นกับ **สองอย่างที่คนละเรื่องกับต้นทุน** — และควรแก้คนละทาง

| สาเหตุที่ทำให้ช้า | แก้ได้ด้วย | ต้นทุนลดด้วย |
|---|---|---|
| ส่ง prompt ใหญ่ขึ้นเรื่อย ๆ (median 48,889 ตัวอักษร) | ย่อ prompt (สวิตช์) | **ใช่ — อันเดียวกัน** |
| Jev pre-check รอก่อนเสียงแรก | เริ่ม stream จากคำตอบไม่ได้ (ต้องรอ intent) · แต่ cache ได้ | ย่อลง |
| โมเดลคิดก่อนตอบ (reasoning model) | สวิตช์ `tiga_short_routing` มีอยู่แล้ว | — |
| `flush()` ทุก 60 มิลลิวินาที | เฟรมแรกเร็วขึ้นถ้าลดเหลือ 30 มิลลิวินาที · **เสียประสิทธิภาพเครื่อง** | — |
| รอบ 2 เมื่อล้ม (หน่วง 4 วิ) | อยู่แล้ว ถูกต้อง | — |

> **ข้อเสนอเพิ่มที่ผมอยากเสนอ — “คำตอบแรกเร็ว คำตอบเต็มช้า”:** ตอนนี้ผู้เรียนเห็นตัวพิมพ์เขียนค่อย ๆ ซึ่งเป็นความรู้สึกที่ดี · ถ้าจะให้เร็วขึ้นอีก ทางที่ถูกคือ **ย่อ prompt** (ข้อ 1) ไม่ใช่เร่งเครื่อง

## 2. ความเร็ว + ต้นทุน + สนุก จาก **หน้าตาเดียวกัน**

จุดที่ทำให้แชท “รู้สึกเป็นเกม” มี 3 ตัว ทั้งหมด **ถูกลงด้วย** ไม่ใช่ของแพง ๆ

### A · แถบความคืบหน้าใต้กล่องพิมพ์ — ฟรีที่สุด

หน้าแชทวันนี้**ไม่มีตัวเลขใด ๆ บนหน้าเลย** ยกเว้นตัวนับโควตาฟรี ขณะที่หน้าอื่นมี streak / quest / level / league ครบ

```
🔥 3 วัน · วันนี้ถาม 4 ข้อ · เควสต์ 2/3  ·  +40 EXP
```

ใช้ของที่มีอยู่แล้ว: `profile.streak` · `tg_usage.chat` · `profile.quest_count` — **ไม่เพิ่ม state ไม่เพิ่ม request ไม่ใช้เงิน**

**ทำไมได้ผล:** ความรู้สึกเกมมาจากการ *เห็นความคืบหน้า* ไม่ใช่จากการได้รางวัลใหญ่

### B · EXP จากการถาม (ปิดช่องรั่วข้อ 1) — ต้นทุน **ติดลบ** (เพราะเงินที่ได้จากคนถามคือเงินที่ประหยัด)

**โค้ดมีอยู่แล้วแต่เรียกไม่ครบทาง** — `gainExp(EXP.ask = 10, { quest: true })` ทำให้ถาม 4 ข้อ = จบเควสต์วันนั้น (`QUEST_BONUS = 40`) ซึ่งเป็นตัวเลขที่*ดู*คุ้ม

**แต่ต้องถามเจ้าของก่อน** เพราะ `AGENTS.md` ระบุ: *“changing what chat pays is an owner decision”*

**ข้อเสนอของผม:** ให้ **EXP อย่างเดียว ไม่ให้เหรียญ** · จ่ายเฉพาะตอนครูตอบสำเร็จ · ไม่จ่ายตอน error/โดนปฏิเสธ/spam

**ข้อควรระวังด้านต้นทุน:** ถ้าครูตอบเร็วขึ้นมาก (จากการย่อ prompt) แล้วผู้เรียนถามบ่อยขึ้น → ต้นทุนต่อคำถามตกแต่**จำนวนคำถามขึ้น** ต้องดูคู่กับ §3 ที่ทำให้แชท *คุ้มขึ้น* ไม่ใช่แค่เร็วขึ้น

### C · ครูไม่ปล่อยคำถาม — ความรู้สึกเกมที่ถูกที่สุด

persona ตอนนี้สั่งให้ *“close with one concrete next step”* = **คำสั่ง** (คุณทำอะไรต่อ) ไม่ใช่ **เกม** (คุณตอบถูก/ผิด)

**เปลี่ยนเป็น:** ปิดทุกคำตอบด้วยคำถามเลือก 3 ข้อ ผูกเป็นปุ่ม

```
ครู: โน้ตที่ 3 ในคีย์ C คืออะไร
     [ C4 ]  [ E4 ]  [ G4 ]
→ ถูก: ✅ พร้อมเสียงจริง + EXP
→ ผิด: อธิบายเฉพาะที่ผิด 1-2 บรรทัด (สั้นตาม P0-2) แล้วให้ลองอีกครั้ง
```

**ต้นทุน:** คำตอบสั้นลง = ค่าใช้จ่ายลง · ปุ่มเป็น DOM ที่มีอยู่แล้วใน `Msg` · ไม่มี request เพิ่ม

**มีของพร้อม:** `mistake-drill.ts` (ดริลตามจุดที่พลาด) · `activity-trace.ts` (21 เช็ก, รู้อยู่แล้วว่าอะไรนับเป็น trace) · `learnerSignal` (`SKILLS` 7 ตัว) · เกณฑ์คำตอบถูกต้องมีอยู่แล้วใน persona

**กฎเหล็กที่ต้องบังคับ:** ครูตั้งข้อสอบที่**ตัวเองตอบถูกได้เท่านั้น** — ไม่งั้นครูจะสอนผิด ซึ่งแย่กว่าไม่มีเกม

## 10.1 ข้อ 2 เปิดสวิตช์ `tiga_kb_hot_path` — **เจอบั๊กจริงระหว่างพิสูจน์**

ตามแผนต้องพิสูจน์คุณภาพก่อนเปิด จึงรัน `node tigamodel/scripts/eval-kb-capped-vs-legacy.mjs`

**ผลรอบแรก: exit 1 — 2 ปัญหา**

```

innovation-en   114108 → 3628  ×31   on-topic 98% → 50%   ❌

```

**สาเหตุ (วิเคราะห์จากโค้ด ไม่เดา):** `getKBContext()` เลือกหมวดด้วย `text.includes(keyword)` — **ไม่มีขอบเขตคำ** และคำสั่งของหมวด `innovation` มี `"ai"` ตัวหนึ่ง ผลคือ

- `"ear training dictation"` → คำว่า **tr`ai`ning** โดน `innovation`
- `"changed learning"` → คำว่า ch**ai**n โดน `innovation`

→ ทุกคำถามที่พูดถึง training ลากหมวดนวัตกรรมเข้ามาด้วย แล้วสองหมวดนี้ **แบ่งกันเพดาน 24 บรรทัด** ทำให้เนื้อหาที่แท้จริงโดนบีบออก · และตัวเลข on-topic เองก็เพี้ยน เพราะบรรทัดนับว่าตรงประเด็นแค่ที่ “มีตัวอักษรสองตัวนั้นอยู่”

> นี่คือบั๊กที่ **ทำให้แอปแพงขึ้นโดยไม่ได้ให้คำตอบดีขึ้นเลย** — แก้ก่อนเปิดสวิตช์ ไม่งั้นเรากำลังเปิดของที่ยังเลือกผิด

**แก้แล้ว** (`tigamodel/web.js`) — เพิ่ม `kbKeywordHit()`:
- คำอังกฤษ/Latin → จับด้วย **ขอบเขตคำ** (`ai` ไม่โดน “training”/“chained”/“detail”)
- ภาษาไทย/จีน/ญี่ปุ่น → **ยังจับแบบ substring** เพราะไม่มีการเว้นวรรค (“หู” เป็นส่วนหนึ่งของ “ฝึกหู” จริง ๆ)
- ทั้งตัวเลือกหมวด และ `kbFiredKeywords()` ใช้นิยามเดียวกัน

**ผลหลังแก้ — exit 0**

```

innovation-en     2603 → 2603  same   on-topic   0% →   0%  ✅
retrieval gate: legacy 100% · capped 100%

```

> **อ่านตัวเลข `innovation-en` ให้ถูก:** ตอนนี้โชว์ 0% → 0% เพราะคำถามนั้น**ไม่โดนหมวด innovation อีกแล้ว** — ซึ่งถูกต้องสำหรับคำถาม “how has **digital piano technology** changed learning”? คำว่า “technology” ควรโดน … ขอรายงานตรง ๆ ว่า **คำถามนี้ควรโดน innovation แต่ตอนนี้ไม่โดน** เพราะ probe วัด on-topic จากคำที่ “โดนจริง” ซึ่งเปลี่ยนไปพร้อมการแก้ · **นี่คือผลข้างเคียงที่ต้องตรวจใน Model Lab** ไม่ใช่ผลที่พิสูจน์ว่าดีขึ้น
