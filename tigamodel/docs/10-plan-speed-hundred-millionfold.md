# 10 — แผนความเร็ว: เร็วกว่าเดิม 100 ล้านเท่า โดย**ไม่หลอน ไม่ตอบผิด เก่งเท่าเดิม**

ต่อจาก docs/05–09 (คุณภาพ → การวัด → บังคับตัวเอง → กฎหมาย → ระบบนิเวศ) — แผนนี้ตอบโจทย์ที่
เจ้าของสั่ง (2026-09-29): **ความเร็วเป็นเป้าหมายใหญ่ถัดไป แต่ห้ามแลกด้วยความถูกต้อง**

> สูตรเหล็กของแผนนี้: **เร็ว = ไม่ต้องคิดซ้ำในสิ่งที่รู้คำตอบแล้ว**
> ไม่ใช่ "เร็ว = ตอบเร็วขึ้นโดยไม่ตรวจ" — ทางลัดทุกชนิดที่เสี่ยงความถูกต้องห้ามใช้

## ส่วนที่ 1: ความเร็วมาจากไหนได้บ้าง (เรียงตามหลักฐานยืนยันได้)

| ทาง | กลไก | ทำไมไม่หลอน | สถานะ |
|---|---|---|---|
| **1) จำคำตอบที่พิสูจน์แล้ว** (answer cache) | คำถามเดิมเป๊ะ ๆ → คืนคำตอบที่เคยผ่านการตรวจจาก provider จริง **พร้อมบันทึกที่มาเดิมทุกตัวอักษร** | เก็บเฉพาะคำตอบ `status:"ok"` + confidence ผ่านเกณฑ์ — `uncertain`/`error` **ห้ามจำเด็ดขาด**; คำตอบจำได้ = คำตอบที่เคยถูกตรวจแล้ว ไม่ใช่เดาใหม่ | ✅ m32 ส่งมอบแล้ว |
| **2) สมองกฎเร็วอยู่แล้ว — วัดให้เห็น** | teaching policy + KB context เป็น pure code (ไม่ยิงเครือข่าย) — scorecard ด่าน 8 วัดจริงทุกรอบ | วัดของจริง ไม่ใช่คำสัญญา | ✅ m33 ส่งมอบแล้ว (scorecard ด่าน 8) |
| 3) หน่วยความจำคำถามยอดฮิต (KB hot set) | จัดลำดับ KB ให้คำถามที่พบบ่อยค้นเจอก่อน (การจัดลำดับไม่แตะเนื้อหา) | เนื้อหาเดิม 100% แค่เปลี่ยนลำดับการมอง | m34 |
| 4) ข้ามเส้นทางที่ไม่จำเป็น | routing ไม่ผ่าน provider ที่แพง/ช้าสำหรับงานเล็ก (ต่อยอด cost governor §8) | คุณภาพยังอยู่ในเงื่อนไขร่วมของ m22 (eval ต้องผ่านเท่าเดิม) | m35 (คู่กับ m22) |
| 5) ขอบเขตความเร็วของโมเดลภายนอก | เวลา call provider จริง: budget ต่อ task + timeout อัตโนมัติ → ตอบช้า = ตอบด้วยกฎของเราแทน | คำตอบสำรองมาจาก KB/กฎที่ตรวจแล้ว ไม่ใช่การเดา | m36 |

## ส่วนที่ 2: สิ่งที่ห้ามทำเด็ดขาด (กัน "เร็วขึ้นแต่หลอนมากขึ้น")

1. **ห้าม cache คำตอบที่ไม่แน่ใจ** — `uncertain`/`error`/confidence ต่ำกว่าเกณฑ์ = ไม่มีวันเข้า cache
2. **ห้าม cache ข้ามบริบทนักเรียน** — คีย์ cache รวมสิ่งที่ทำให้คำตอบต่างกันได้ (คำถาม/ประวัติแชท) — บริบทต่าง = คำตอบต่าง
3. **ห้ามตัดขั้นตอนตรวจเพื่อความเร็ว** — eval suite/plan-check/scorecard ยังบังคับทุก merge เหมือนเดิม (กติกาเหล็กข้อ 2/6)
4. **ห้ามแต่งตัวเลข latency** — scorecard ด่าน 8 วัดจริงทุกรอบ ค่าที่อวดต้องมาจากเครื่องเดียวกับที่รัน
5. **ทุกกลไกเร็วต้องปิดได้ใน 1 นาที** (กติกาเหล็กข้อ 5) — answer cache มี kill switch ตั้งแต่วันแรก

## ส่วนที่ 3: ไมล์สโตน (ต่อท้ายแผนรวม — m32 เริ่มที่นี่)

| id | สิ่งที่ส่งมอบ | เกณฑ์ "เสร็จ" | สถานะ |
|---|---|---|---|
| m32 | Answer cache ที่จำได้เฉพาะคำตอบที่มีที่มา + kill switch | smoke: ok เท่านั้นที่ถูกจำ · uncertain/error ไม่ถูกจำ · บริบทต่าง = คีย์ต่าง · สวิตช์ปิด = ไม่จำ · พร้อมน้ำหนัก จำกัดขนาด | ✅ done |
| m33 | scorecard ด่าน 8: ความเร็วที่วัดจริงของสมองกฎ/KB | วัดจริงทุกรอบ + บาร์ที่สมเหตุผล (KB < 100ms, policy < 20ms) | ✅ done |
| m34 | KB hot-set ordering (คำถามยอดฮิตเจอก่อน) | retrieval gate ยัง ≥80% + คำถาม probe 10 อันดับแรกเร็วขึ้นวัดได้ | planned |
| m35 | routing สายสั้นสำหรับงานเล็ก (คู่ m22) | eval suite ผ่านเท่าเดิม + ต้นทุน/latency p95 ลดตามเป้า §8 | planned |
| m36 | timeout/budget ต่อ provider call | provider ช้าเกิน budget → ตอบด้วยกฎ/KB ของเรา (มีที่มา) ไม่ห้อย | planned |

## ส่วนที่ 4: ทำไม "เร็ว 100 ล้านเท่า" จึงเป็นทิศทาง ไม่ใช่ตัวเลขสัญญา

100 ล้านเท่าวัดต่อเส้นทางไม่ได้ด้วยการวิ่งให้เร็วขึ้น — แต่ได้ด้วย **การไม่ต้องวิ่ง**:
คำถามที่ตอบแล้ว (cache มีที่มา) เร็วขึ้นหลายระดับจากหลักพัน ms เหลือหลัก ms ·
สมองกฎไม่เคยต้องรอเครือข่าย · งานเล็กไม่ต้องต่อคิวโมเดลใหญ่ · และทุกทางลัด
**ผ่านประตูความถูกต้องเดิมเสมอ** — eval + retrieval gate + plan-check + scorecard ยังยืนกันด่านอยู่ครบ

> ความเร็วที่ยอมรับได้ = ความเร็วที่ **พิสูจน์ว่าคำตอบไม่เปลี่ยนคุณภาพ** —
> นี่คือเหตุผลที่แผนนี้ผูกทุกไมล์สโตนกับ "eval ผ่านเท่าเดิม" เป็นเงื่อนไขร่วมทุกข้อ
