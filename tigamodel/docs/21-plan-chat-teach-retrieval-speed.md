# 21 — แผน v3: TIGA CHAT ให้ **สอนได้จริง** · **ใช้องค์ความรู้ที่ Train มา** · **ตอบเร็วขึ้น 100 เท่า** (เจ้าของสั่ง 2026-10-03)

ต่อจากเอกสาร 20 (`20-plan-chat-fun-megaton.md` = "สนุกขึ้น") · เอกสารนี้ตอบ 3 คำถามที่เจ้าของถามมา และ**แก้ความผิดพลาดของแผนเอง**

## 0. ตอบคำถามเจ้าของก่อน (สั้น ๆ แล้วลงรายละเอียด)

### Q1 · "ฟีเจอร์ TIGA Chat ได้ดึงองค์ความรู้ที่เรา Train Model TIGA Model มาใช้หรือยัง?"

**ตอบ: ดึงมาใช้แล้ว — แต่ใช้ไม่ครบ 3 ใน 4 ชั้น**

หลักฐานจากโค้ด (`use-chat.ts:358-364`, `tigamodel/web.js:1423`):

```js
const hub = tigaNow();                              // ← โหลด TIGA Model แบบ lazy
const kbContext   = await hub.getFullKBContext(userText);   // ← องค์ความรู้หลัก
const studentBlock = hub.getStudentContextBlock();          // ← ใครคือผู้เรียน
const coachBlock   = hub.getCoachContextBlock();            // ← WHAT/WHY/HOW จากตัวเลขจริง
```

| # | ชั้นความรู้ | แหล่ง | สถานะ | ขนาดจริง |
|---|---|---|---|---|
| 1 | **KB หลัก** (17,246 รายการ) | `getKBContext()` | ✅ ใช้อยู่ | **1.4 KB – 1.38 MB** ตามคำถาม |
| 2 | **ความรู้ที่เจ้าของสอนเอง** (LEARNED) | `ensureSelfLearner().getLearnedKBContext()` | ⚠️ **มีโค้ดแต่ปิดอยู่** — `if (!s.enabled) return ""` | **0 ตัวอักษร** |
| 3 | **บริบทผู้เรียน** (student + coach) | `getStudentContextBlock()` / `getCoachContextBlock()` | ✅ ใช้อยู่ | 332 + 604 = **936 ตัวอักษร** |
| 4 | **ความรู้ที่โมเดลเรียนรู้เพิ่มเอง** (self-learn strategies) | `e.strategy` ถูก**กรองทิ้ง** | ❌ **ไม่เคยถูกใช้** | **0** |

**ชั้นที่ 2 สำคัญที่สุด** เพราะเป็นองค์ความรู้ที่เจ้าของ Train มาเอง — และมัน
ถูกตัดด้วย `if (!s.enabled) return ""` ที่ `self-learner.js:181` ซึ่งเป็นสวิตช์ (กฎห้ามเปิดจากโค้ด → **เจ้าของเปิดเอง**)
โค้ดเดียวกันมีคอมเมนต์ยอมรับว่าเคยพลาด:
> `BUGFIX (owner directive "ใช้ได้จริงๆ"): was \`if (_learner)\` — but _learner is null until
> someone calls ensureSelfLearner(), so production chat NEVER received learned knowledge`

**ชั้นที่ 4** ถูกกรองทิ้งที่ `getLearnedKBContext` บรรทัด 182: `.filter(e => !e.strategy)` —
คือทุกอย่างที่ TIGA Model เรียนรู้จากการใช้งานจริง **ถูกตัดออกจากแชททั้งหมด**

### Q2 · "ถ้ายังเอามาใช้ด้วย ต้องมีความเร็วในการตอบแชทที่สูงขึ้นด้วย"

**ตอบ: ตอนนี้ช้าเพราะ "ดึงผิดที่" ไม่ใช่เพราะดึงเยอะ**

วัดจริง 4 คำถาม (`measure-chat-cost.mjs --question`):

| คำถาม | KB ที่ดึงมา | รวม prompt | มี keyword ตรงไหม |
|---|---|---|---|
| `major chord คืออะไร` | **1,383,891** | 1,392,371 | มี (แต่ดึงทั้งหมวด) |
| `อะไรทำให้เพลงฟังดูมีชีวิต` | 111,665 | 120,145 | มี |
| `อยากรู้ว่าทำไมมือซ้ายถึงซ้อนเสียง` | 51,427 | 59,907 | **ไม่มี** |
| `ช่วยอธิบายเรื่องนี้หน่อย` | 40,768 | 49,248 | **ไม่มี** |

**ช่องว่าง ~990 เท่า** (1.38M → 1.4K) ทั้งหมดขึ้นกับ **คำเดียว: `kbKeywordHit()`**
ยืนยันว่าไม่มี semantic search: `grep -niE "embedding|vector|cosine|similarity|rag"`
เจอ **ศูนย์ตัว** → ค้นด้วย keyword ล้วน

### Q3 · "เพิ่มเรื่องการสอนให้มีประสิทธิภาพมากขึ้นด้วย"

**ตอบ: วงจรการสอนยังไม่ปิด** — ครูสอน → ผู้เรียนทำ → **แล้วไม่มีการตรวจว่าได้ผลจริง**

| ขั้น | สถานะ |
|---|---|
| ครูสอน | ✅ `markUnderstood` → `recordMemory(label, acc)` (`App.tsx:11683`) |
| ผู้เรียนลงมือทำ | ✅ ปุ่ม `.actbtn` พาไปฝึกจริง |
| **ตรวจว่าได้ผลไหม** | ❌ **ไม่มี** — `grep "accAfter\|retest\|verify_learned"` = ศูนย์ตัว |
| ครูรู้ว่าผู้เรียนติดอะไรขณะนั้น | ❌ **`learnerSignal` ไม่เคยเข้าแชท** — เอกสาร 19 §2-F เสนอไว้แต่ไม่ได้ทำ |

## 1. รากของปัญหาทั้งสามข้อ คือสิ่งเดียวกัน

> **แชทรู้ "คำถาม" แต่ไม่รู้ "ผู้เรียนคนนี้ต้องการอะไรตอนนี้"**

- ค้น KB ด้วย keyword → คำถามที่เป็นภาษาธรรมดาได้ 1.38 MB (ช้า แพง)
- ไม่รู้ว่าเขาเคยติดอะไร → สอนแบบเหมารวม ไม่ใช่แก้จุดที่เขาล้ม
- ไม่วัดผลหลังสอน → ไม่มีทางรู้ว่าครูดีขึ้นไหม

**แกนของแผนนี้:** แทนที่จะ "ดึง KB เยอะแล้วให้โมเดลตัดสินเอง"
→ **หาบล็อกความรู้ที่ใช่ด้วยกติกาที่วัดได้ แล้วส่งเฉพาะอันนั้น**

## 3. แกนแผน: 4 เฟส เรียงตาม "ของที่ได้ก่อน"

### ★ V1 · **RETRRIEVAL ที่เลือกได้** — แก้รากความช้า 1.38M → ~3K
> *แทนที่จะให้โมเดลอ่านทั้งหมด → เลือกให้เหลือเท่าที่พอ*

**ปัญหา:** `getKBContext()` คืน **บรรทัดทั้งหมวด** ถ้าคำถามแตะหมวดใด → หมวดนั้นทั้งก้อน
(`major chord` → ดึง 1,383,891 ตัวอักษร)

**แก้ 3 ชั้น เรียงจากถูกไปเสีย:**

| ชั้น | วิธี | ผล |
|---|---|---|
| **a. เพดานต่อคำถาม** | ตัด hard cap ที่ระดับ KB (ไม่ใช่ระดับ category) | 1.38M → **≤ 12,000** ทุกคำถาม |
| **b. ให้คะแนนบรรทัด** | บรรทัดที่มีคำจากคำถามจริง → เก็บก่อน เพดานเต็ม | คำถามตรงประเด็นได้คำตอบที่ตรง |
| **c. cache ตามคำถาม** | คำถามเดิม → ใช้ผลเดิม (`withAiCache` — **มีอยู่แล้วแต่ไม่ถูกเรียก**) | คำถามซ้ำ = **0 token** |

**พิสูจน์:** `measure-chat-cost.mjs --question` ต้องให้ **ทุกคำถาม < 15,000**
และ `eval-kb-capped-vs-legacy.mjs` ต้องยัง **exit 0** (คุณภาพห้ามตก)
→ ถ้าตก แปลว่าเพดานตัดความรู้จริง → **ต้องแก้การจัดอันดับ ไม่ใช่ยกเพดาน**

---

### ★ V2 · **ส่งความรู้ตามคำถาม ไม่ใช่ส่งตายทุกครั้ง**
> *`THEORY_REF` 4,070 + `FINGERING_REF` 1,142 = 61.5% ของ prompt ตายตัว · ส่งทุกคำถามแม้ไม่เกี่ยว*

ปัจจุบันส่งทั้งสองอย่าง **ทุกคำถาม** (`use-chat.ts:384`) ไม่ว่าถามเรื่องกติริยา เมื้อ หรือทำนอง
แก้เป็น **เลือกส่ง** ตามคำถาม (คำเดียวกับ `kbKeywordHit` ที่ตรวจไว้แล้ว):

| คำถามเกี่ยวกับ | ส่ง |
|---|---|
| ทำนอง/เทคนิค | `FINGERING_REF` เท่านั้น |
| ทฤษฎี/บันทึกเสียง | `THEORY_REF` เท่านั้น |
| ผสม/กว้างๆ | ทั้งคู่ |

**ผลที่วัดได้:** ส่วนคงที่เฉลี่ย **8,480 → ~5,300** (−37%) โดย **ไม่ลดความรู้ที่ตรงกับคำถามลงเลย**
**พิสูจน์:** สคริปต์เดิม + เพิ่มเช็กว่าคำถามทฤษฎียังได้ `THEORY_REF` ครบ

---

### ★ V3 · **เปิดชั้นความรู้ที่ Train มา (ชั้น 2 + 4)** — แก้ "ดึงมาไม่ครบ"
> *เจ้าของสอนครูเอง แต่ครูไม่เคยได้อ่าน*

| ชั้น | ต้องทำ | ใครทำ |
|---|---|---|
| **2 · LEARNED** | เปิดสวิตช์ `self_learner.enabled` + ทดสอบว่าครูอ่านได้จริง | **เจ้าของเปิด** (เขียน `app_settings` production) |
| **4 · strategies** | เอาออกจาก `.filter(e => !e.strategy)` — **แต่ต้องเพิ่มเพดานความเชื่อถือก่อน** | ผมทำ (ไม่ต้องขออนุมัติ) |

**ข้อควรระวังที่ต้องบอกตรง ๆ — ชั้น 4:**
ตอนนี้ทิ้ง `strategy` เพราะของมันคุณภาพไม่แน่นอน ถ้าเอามาใช้เลยอาจทำให้ครูสอนผิด
→ ผมจะใส่เงื่อนไขตามที่โค้ดเตรียมไว้แล้ว: `CONF_MAX_ADMIN = 0.8` · `CONF_MAX_REINFORCED = 0.85`
คือ **ใช้เฉพาะรายการที่เจ้าของยืนยัน (confidence ≥ 0.8) หรือถูกยืนยันซ้ำ (≥ 0.85) เท่านั้น**
และเพดาน 6 รายการแรกตามความมั่นใจ — เหตุผลที่โค้ดเขียนไว้เอง ผมจะไม่ข้าม

**พิสูจน์:** smoke ที่ยืนยันว่า entry ที่ `enabled=false` ยัง**ไม่ถูกส่ง** (default OFF เหมือนทุก kill switch ก่อนหน้า)

---

### ★ V4 · **ปิดวงจรการสอน + ให้ครูรู้ว่าผู้เรียนติดอะไร**
> *"ครูสอนแล้ว ไม่มีใครเช็คว่าเขาเข้าใจจริงไหม"*

| ขั้น | งาน | ต้นทุน |
|---|---|---|
| **4a. วัดผลหลังสอน** | ผู้เรียนกด `.actbtn` ไปฝึก → **ครูถามกลับวันรอบถัดไปว่าได้ผลไหม** | บันทึก label + วันที่ลงมือทำ (มีอยู่แล้วใน `recordMemory`) |
| **4b. `learnerSignal` เข้าแชท** | เข้า prompt ตามเอกสาร 19 §2-F — **ทำแล้วค้างมา ไม่เคยลงมือ** | ขนาดเพิ่ม **~150 ตัวอักษร** (เล็กกว่า V2 ที่ประหยัด 5,210) |
| **4c. ครูไม่อธิบายซ้ำเรื่องที่เขารู้แล้ว** | ตัด `mastered` ออกจากบริบทเมื่อถามซ้ำ | ลด prompt + สอนตรงจุดขึ้น |

**เหตุผลที่ 4b คุ้ม:** ขนาดที่เพิ่ม **150 ตัวอักษร** เทียบกับ V2 ที่ประหยัดได้ **3,000+**
และ `memoryContext()` ตอนนี้ยาวสูงสุดแค่ **428 ตัวอักษร** (วัดแล้ว) → เพิ่ม `learnerSignal` ไม่ทำให้ช้า

**แก้ที่บรรทัดเดียว:** `getKBContext()` วนทั้งหมวดโดยไม่มีเพดาน ทำให้คำถามเดียวลากมา 1.38 MB

และจัดอันดับด้วย `rankKbLines()` — ในหมวดเรียงตาม keyword ที่ยิงจริง · ข้ามหมวดสลับกัน (round-robin) ไม่ให้หมวดใดกินเพดานหมด

## 10.2 เฟส 1 — `learnerSignal` เข้าแชต (V4b)

- `learnerSignalContext(lang, signal)` ใน `ai-chat-context.ts` → สร้างบล็อก "เล็งตรงนี้" ให้ครู
- อ่าน `learnerSignal()` ตัวเดียวกับที่ Mentor card ใช้ → ครูกับการ์ด **ตั้งชื่อจุดอ่อนไม่ขัดกัน**
- **`nextAction = null` → คืน `""` ไม่เดา** (กติกาช่องว่างตามจริง — ครูที่กุความรู้ผิดแย่กว่าครูที่เงียบ)
- เพิ่ม ~150 ตัวอักษร · **ไม่มี model call เพิ่ม** · `actTopicLabel` export จาก `App.tsx` ให้ใช้ร่วม

## 10.3 เฟส 2 — ส่ง REF ตามคำถาม (V2)

- `refForQuestion(text)` → ส่ง `THEORY_REF` / `FINGERING_REF` เฉพาะเมื่อคำถามแตะเรื่องนั้น
- **กติกาไม่สมมาตรอย่างตั้งใจ:** ไม่ชัด → ส่ง **ทั้งคู่** (เหมือนเดิม) · ชัดเรื่องเดียว → ส่งเฉพาะอันนั้น
- เหตุผล: ส่งเกิน = เปลืองโทเคน · ไม่ส่งที่ต้องใช้ = ครูตอบผิดเรื่องการทำนอง
- 5,212 ตัวอักษร = **61.5%** ของ prompt ตายตัว ไม่ต้องจ่ายทุกข้อครั้งแล้ว

## 10.4 เฟส 3 — Retrieval (V1a+b)

### บั๊ก 3 ตัวที่เจอระหว่างทำ และแก้จากสาเหตุ ไม่ใช่ปรับเกณฑ์

| # | บั๊ก | พิสูจน์ | แก้ |
|---|---|---|---|
| 1 | จัดอันดับด้วยคะแนนล้วน → `performance-th` 63%→29%, `harmony-en` 100%→17% | stash โค้ดเดิมมารัน = **exit 0** ก่อนงานนี้ → เป็นงานผมจริง | เปลี่ยนเป็น round-robin ต่อหมวด (รูปแบบเดียวกับที่วัดได้ 100%) |
| 2 | ไม่มี semantic search (`grep embedding\|vector\|cosine` = **0**) → การดึงผิดที่ | `measure-chat-cost` วัด 4 แบบคำถาม | เพดาน + จัดอันดับในหมวดที่คำถามยิงจริง |
| 3 | หมวด HARMONY มี 40 บรรทัด → กินเพดาน 24 ช่องเอง หมวด ACCOMPANIMENT หายทั้งหมด | `dbg14`: `{"HARMONY":24}` | แต่ละหมวดได้ 1 บรรทัด **ก่อน** ใครจะได้บรรทัดที่สอง |

### `relScoreOf` — จุดที่ทำให้ hot path แย่ (แก้ใน hot path เพราะเป็นสาเหตุจริง)

KB มีตระกูล "A อยู่ในคอร์ด X ไหม" 20 รายการ ซึ่งเป็น **คำถามให้ผู้เรียนตอบ** ไม่ใช่เนื้อหาสอน
แต่ `teach` ของมันมีคำเดียวกับที่คำถามยิง → ได้คะแนนเท่ากันเป็นบรรทัดสอนจริง → เบียดบรรทัดที่ตอบคำถามได้ออกไป
**แก้:** entry ที่เป็นคำถาม (`…ไหม` / ลงท้าย `?`) ให้คะแนนจาก **title เท่านั้น** ไม่ดู `teach`
(ลองตัด `teach` ออกทั้งหมดก่อน — ผิดอีกทาง ทำให้ `sight-th` ตกเหลือ 50% เพราะเลขระดับคือตัวสอน)

## 10.5 เกณฑ์ที่เพิ่มใน eval (เพิ่ม ไม่ใช่ผ่อน)

`eval-kb-capped-vs-legacy.mjs` เดิมเทียบ hot path กับ legacy ซึ่งหลังจากนี้ "legacy" มีเพดานของมันเองแล้ว
จึงเพิ่ม `uncappedKbLines()` = การขยายทั้งหมวดแบบก่อนแก้ เป็น baseline จริง แล้วตรวจว่า **เพดานทำให้หมวดที่คำถามแตะหายไปหรือไม่**

เกณฑ์ 2 ข้อที่ลองแล้ว **ผิด และถูกเอาออก** (พร้อมเหตุผลที่วัดได้):
- "ทุก keyword ที่ยิงต้องปรากฏ" → `scale` ไม่ปรากฏใน **799 บรรทัด** ของ uncapped ด้วย → วัดผิดสิ่ง
- "ต้องเก็บ x% ของบรรทัดตรงประเด็น" → คำถามเดียวมี 12,166 บรรทัดตรงประเด็น เก็บ 77 = 0.6% แต่ retrieval ยัง 100% → นับปริมาณของบล็อกเก่า ไม่ใช่คุณภาพ
