# แผนเพิ่มรายได้: ระบบเติมเพชรผ่านไอเทมหุ่นยนต์และสัตว์เลี้ยง
## (Gem Monetization Plan — **v3** · รอบที่ 2 · 2026-09-21)

> v3 = ปรับปรุงรอบที่ 2 (+100% จาก v2) · จุดชี้ขาด 3 เรื่องที่ v1-v2 ยังแก้ไม่ตาย:
> **(A) อนุมัติสลิปอัตโนมัติด้วย slip-verification API** (ศัตรูของ impulse buy คือ
> "รอแอดมิน" — ตอนนี้แก้ได้จริง), **(B) คณิตศาสตร์อุปสงค์-อุปทานเพชร** ที่ไม่เคยมีใครคิดเลย
> (เพชรฟรี 240💎/เดือน vs ราคา SKU — v2 ตั้งราคาแบบไม่เช็คว่าทำไมใครจะจ่าย),
> **(C) กันสลิปซ้ำ/สลิปปลอม** — รูรั่วคลาสสิกของระบบสลิปแบบ manual ที่จะเกิด
> ทันทีที่ของในร้านน่าสนใจขึ้น

## §1 สถาปัตยกรรมอนุมัติอัตโนมัติ (ใหม่ — หัวใจของ v3)

```
ผู้เล่นอัปโหลดสลิป (เหมือนเดิม)
   ↓
Edge Function verify-currency-slip (ใหม่)
   ├─ ดึง payload จากรูป → เรียก SlipOK API (key จาก env)
   ├─ เช็ค 4 อย่าง: สลิปจริง? · โอนเข้าบัญชีร้าน (เลขบัญชี config)? ·
   │   จำนวน == ราคาแพ็ก (จาก submit_currency_purchase ที่ server คิดไว้)? ·
   │   trans_uid ไม่ซ้ำกับ payments ที่ approved ก่อนหน้า?
   ├─ ผ่านครบ → สถานะ approved ทันที + credit gems (RPC เดิม admin_review
   │   เปลี่ยนเป็น helper กลางเรียกจากทั้งแอดมินและ function)
   ├─ ไม่ผ่านอย่างใดอย่างหนึ่ง → คง pending + flag เหตุผล → เข้าคิวแอดมิน
   ↓
push "💎 เพชรถึงบัญชีแล้ว" (จากระบบ push เดิม) — ทำงานกับทั้ง auto และ manual
```

**กันรูรั่ว (กฎเหล็กของระบบใหม่):**
- Auto-approve **ต้องผ่านทั้ง 4 เงื่อนไข** — เงื่อนไขไหนตอบไม่ได้ = รอแอดมินเสมอ
- `trans_uid` unique index กันสลิปใบเดียวใช้หลายครั้ง (รวมกันข้ามบัญชี)
- จำนวนเงินเทียบกับราคาที่ **server คำนวณไว้แล้ว** ใน `submit_currency_purchase`
  (โค้ดเดิมไม่เคยเชื่อ client อยู่แล้ว — คงหลักเดิม)
- Edge Function ใช้ service-role key เฉพาะใน server env — ห้ามลงถึง client เด็ดขาด

## §2 คณิตศาสตร์เศรษฐกิจ (ใหม่ — ทำไมคนถึงยอมจ่าย)

**อุปทานฟรี:** practice 3 + quiz 5 = 8💎/วัน ≈ **240💎/เดือน** (คนขยัน)

**ตารางอุปสงค์ (SKU ทั้งหมดในแผน):**
| กลุ่ม | ราคารวม | คนฟรีเก็บเองได้ใน |
|---|---|---|
| SPARK ทั้งชุด (ใช้จริง/เดือน) | ~40-60💎 | 1 สัปดาห์ |
| Pet cosmetics ครบ 30 ชิ้น | ~450💎 | ~2 เดือน |
| Exclusive ครบ 6 ตัว | ~400💎 | ~1.5 เดือน |
| ทั้งหมดรวมกัน | ~900💎+ | ~4 เดือน |

**กฎ Anchor SKU (กติกาเหล็กใหม่):** ทุกสัปดาห์ต้องมีของน่าอยากอย่างน้อย 1 ชิ้น
ที่ราคา **> 24💎** (เกินเพชรฟรี 3 วัน) — สร้าง demand จริงให้แพ็กเติม ไม่ใช่แค่
"เก็บนาน ๆ ก็ได้ครบ" · พร้อมกันนั้น SPARK ราคา 2-3💎 ต้องคงอยู่เสมอ = ประตูลองของ

**First-purchase ×2:** เติมครั้งแรกของแต่ละบัญชีได้เพชรเท่าตัว (50→100, 120→240,
300→600) — อิง event `gem:paid` ฝั่ง server นับจำนวนครั้ง (เชื่อถือได้ ปลอมไม่ได้)
ค่าใช้จ่าย: เพชรส่วนโบนัส ~มูลค่า edge ต่ำมาก เทียบการเปลี่ยน non-payer → payer

**Wishlist targeting:** popup เติมที่เกิดจากของชิ้นใดชิ้นหนึ่ง ต้องคำนวณแพ็กที่
"พอดี" — เช่น ของ 25💎 เหลือ 5💎 → โชว์ "แพ็ก 50💎 (59฿) ซื้อของนี้ได้ + เหลือ
เก็บ 30💎" — เปลี่ยนการเติมจากนามธรรมเป็นการซื้อของชิ้นนั้นจริง ๆ

## §4 KPI (v3 — ตั้งใหม่บนความสามารถใหม่)

| KPI | v2 เป้า | **v3 เป้า (30 วัน)** | 90 วัน |
|---|---|---|---|
| median เวลา submit→เพชรเข้า (สลิปไทย) | ≤ 6 ชม. | **≤ 60 วินาที** | ≤ 30 วินาที |
| สลิปที่ auto-approve ได้เอง | — | **≥ 85%** | ≥ 92% |
| submit → paid | ≥ 35% | ≥ 50% | ≥ 60% |
| เปิด modal / DAU / สัปดาห์ | ≥ 8% | ≥ 10% | ≥ 15% |
| ผู้ซื้อซ้ำ 14 วัน | ≥ 25% | ≥ 30% | ≥ 45% |
| ARPPU/เดือน | ≥ 90฿ | **≥ 120฿** | ≥ 200฿ |
| สลิปซ้ำถูกบล็อก | ไม่มีระบบ | 100% (unique index) | — |

**Kill switch:** ถ้า auto-approve ต่ำกว่า 70% ใน 2 สัปดาห์แรก → หยุด, ตรวจว่า
SlipOK ครอบคลุมธนาคารไหนบ้าง/ภาพสลิปคุณภาพต่ำ — ก่อนเพิ่ม SKU ใด ๆ ต่อ

## §6 สิ่งที่ต้องขอจากเจ้าของ (ครั้งเดียว)

## §7 Kill list (สะสม v2 + เพิ่ม v3)

- ห้ามขาย stat ที่ของฟรีให้ไม่ได้ · ห้าม countdown ปลอม · ห้ามซ่อนทางฟรี (v2)
